# D-171 — The AI acts on the project graph it can see: highlight, path search and screenshots
**Status:** accepted (2026-11-12)

**Context.** D-170 deferred the AI half of the graph frontend: "AI tools to highlight paths (`graph_highlight`/`graph_paths`) and to screenshot the graph". The graph family (D-126) reads and writes the committed state, but a chat question about the graph — "where does this page write?", "how does the route reach that table?", "show me the layout" — had no way to act on the panel: the model could not focus what the user was looking at, search connectivity, or see the drawing. Owner decisions (2026-11-12): the path search is undirected (an fk/relation edge connects both ways); the screenshot covers the visible graph, because it answers questions about what the user sees; a focus opens the graph tab automatically.

**Decision.** Three host-side tools in the existing PTC family, no protocol, runner or sandbox change:
- **graph_highlight.** Focuses node/edge ids, validated against the VISIBLE view — the analysis graph with saved positions, hidden edge kinds, collapsed cards and the system filters applied — and opens the graph tab; unknown ids come back as data, an empty request clears the focus. The request is module state (`graph-focus.ts`), replayed once to the next panel mount because the panel unmounts with its tab; it is never written to `.facilis/graph`.
- **graph_paths.** Fewest-hop UNDIRECTED breadth-first search over the visible edges, deterministic tie-breaking, capped at 5 paths / 12 hops. With `to` it returns the single fewest-hop path within `maxHops`; without it, the shortest path to each of the closest `maxPaths` reachable nodes. Unless disabled it focuses the union of the returned paths.
- **graph_screenshot.** Renders the visible view (or the named subset) off-DOM from the view model plus the committed layout: a pure scene builder (`graph-scene.ts`) and a canvas painter (`graph-raster.ts`), JPEG with a 1536 px longest side and quality 0.8, at most two images per program, pushed on the host image side channel that `turn.ts` drains next to preview screenshots (D-112), so the user sees it and a vision preset sends it to the model. No DOM capture, no new dependency; failures are data with a machine reason code.
- **Shared view.** The view construction moved out of React (`graph-view-load.ts`), so tool ids are exactly the ids the canvas renders. The panel dims the cards and edges a request does not name and fits the focus when asked; that programmatic fit is not persisted as the viewport. Specs and the prompt block are advertised only when the host has the graph view.

**Consequences.** Additive: `graph_state`/`graph_arrange` are untouched, no new capability flag, no new persisted state, no source write path (the graph remains diagram state). Focus and screenshots work while the graph tab is closed (replay + off-DOM render). Determinism is bounded by design: cards use the canvas's card sizes rather than live DOM measurements, so a screenshot can differ from the on-screen drawing on very large graphs, and the pixel result is not snapshot-tested (no canvas in Node). Still deferred: mocked-data live preview, component/lib graph nodes (D-134), richer preview facts, DOM-exact capture, and multi-path enumeration for a requested `to`.
