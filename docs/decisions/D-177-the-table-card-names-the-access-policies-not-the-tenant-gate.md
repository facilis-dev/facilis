# D-177 — The table card names the access policies, not the tenant gate
**Status:** accepted (2026-11-12)

**Context.** Owner review of the graph right after D-174: "come vedi ora mi sta mostrando su questa tabella qua la policy RLS tenant ma all'utente interessa poco, interessa l'altra.. la owner policy. si può dare precedenza alle altre policy su tutte le tabelle. Non mostrare proprio nel grafo la tenant policy. la mostri solo nell'elenco." D-174 took the RLS badge off the card, but the card still led with the tenant side of the default class — the scope chip read `tenantId (tenant)` — and the inspector's POLICY section listed `tenant_isolation` first, flagged *restrictive*, while `owner_isolation` — the policy that says who may read the row — came second and plain. The one policy every scoped table has outranked the one that actually distinguishes the table.

**Decision.** The graph names a table's **permissive policies** — the grants (`owner_isolation`, `role_access`, a named `pgPolicy`) — and leaves the **restrictive gate** to the inspector's policy list:
- **Card.** Up to two permissive policy names in declaration order plus a `+N` overflow, in the slot where the tenant scope chip used to be. An owner scope (`ownerId (owner)`) is still named, because it is the exception; `tenantId (tenant)` — the same on every app table — moves to the inspector. A table whose only policy is the tenant gate shows no policy chip.
- **Inspector.** The POLICY list keeps every policy with its command and the *restrictive* flag, ordered grants first and gates last.
- **Facts.** The analyzer carries the declared policy set on the table node (`TableNodeData.policies`, `{name, restrictive}`); the UI selects on the analyzer's `restrictive` flag, never on the literal name `tenant_isolation`, so a project that declares its own gate (or renames it) behaves the same.

**Why.** Precedence follows the security model (D-008/D-136): the restrictive tenant gate only narrows, every reachable app table carries it, and the permissive policy beside it is what grants `facilis_app` access — the fact that makes two tables behave differently. Announcing the default is noise, the same reason D-174 stopped announcing RLS. Selecting by the `restrictive` bit keeps the framework's naming out of the presentation layer and stays true if the gate moves.

**Consequences.** "La mostri solo nell'elenco": the tenant gate and the tenant scope disappear from the cards and remain in the inspector (the scope badge and the POLICY list), so nothing about the security model is hidden — only re-ranked. A table with no permissive policy (the tenant gate alone, a deny-all or broken table) shows nothing, which is honest. Card width is unchanged (at most two chips plus `+N`), so saved `.facilis/graph` layouts keep their positions; the `unknown` classification still comes from the policy facts as before.
