# D-178 — The mini-page follows the page kind: split auth screen, app shell, bare page
**Status:** accepted (2026-11-12)

**Context.** Owner review the same day, after D-176 landed: "ti faccio i complimenti in quanto ora è bello, con le mini paginette … Solo che secondo me non sono proprio 'giuste' nel senso che per esempio la pagina di login e registrazione è fatta leggermente diversamente, magari si potrebbe sfruttare un po di indagine 'semantica' per creare la pagina il più simile possibile a come sarà." D-176 drew every page as the same two-pane app shell, because the shell was the only layout fact it read; the preview facts prove more. In `examples/todo-app` the login/register preview already carries `routePaths: ["/login"]`/`["/register"]` and the chain PublicOnly → AuthLayout → LoginPage → AuthShell, whose real layout is a split brand panel beside a centred card — the mini-page showed it as a one-sided app rail.

**Decision.** `graph-page-sketch.ts` returns a `layout` alongside the shell and blocks, chosen by a pure classifier (`graph-page-layout.ts`) from facts the preview already holds — no analyzer change:
- **auth** when a resolved route path is one of the flow's screens (`/login`, `/register`, `/sign-in`, `/sign-up`, `/forgot-password`, `/reset-password`, `/verify-email`, `/auth`), or, when no route was resolved, when a component is named after the role (`AuthShell`/`AuthLayout`/`LoginPage`/…). The route table is the semantic fact; the name match keeps the sketch useful for a project whose route the analyzer could not resolve. `RequireAuth` deliberately does not match, so a protected page stays an app page.
- **app** when the preview proves a shell (header or rail): the D-176 drawing (rail, optional top bar, weighted content blocks) stays for these pages. **plain** otherwise — a page with no shell (404, standalone screen) draws as one centred column instead of a full-width stack.
- The auth drawing is the split layout: a brand panel (logo, headline lines, points, footer) beside a card with a heading, the form and the footer link. The heading is structural (every auth card opens with one) even though its text arrives through props; the footer link to the sibling screen is one small action.
- Forms now carry the row count the preview proves (`Field > Input` counts once), capped at three, so a login card reads as two fields plus submit instead of a generic form box; a form the budget cut keeps its minimum row.

**Consequences.** Thumbnails differ by page kind and the auth screens read like the shipping layout, at the cost of a heuristic: a project that puts a marketing page under `/auth` or names an unrelated component `Register…` would be drawn as a login screen. The classifier is pure and unit-tested, so tightening it is a test edit. The drawing stays explicitly schematic (no labels, no data, "placeholder data — never a rendering"), and the change adds no analyzer field and no i18n key. The model split keeps each production file under the 300-line limit: node/tree predicates in `graph-page-nodes.ts`, classification in `graph-page-layout.ts`, the model in `graph-page-sketch.ts`, the three drawings in `ProjectGraphPageSketch.tsx`.
