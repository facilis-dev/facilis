# D-179 — Table visibility is one persisted mode; routes are never filtered
**Status:** accepted (2026-11-13)

**Context.** Owner review after D-163 shipped: disabling **Tabelle di sistema non usate** removed tables the project actually uses, and the logout route was no longer associated with `sessions` although the code declares `dbTables: ["sessions"]` for it. Root cause: D-163 classified a route as *system* whenever its `dbTables` named no project-declared relation, which misclassified the starter's auth routes; their `route-table` edges then did not count as project use, so `sessions` and `users` were hidden and the edges vanished with them. The premise is also false: no framework route ever reaches the IDE analyzer — the browser analysis inlines only `@facilis.dev/auth` and `@facilis.dev/db` source (SPEC §5.11, D-130) — so every route the analysis sees is project code and must never be filtered; framework tables are the only framework surface this declutter choice needs to touch.

**Decision.**

- **One mode, three choices.** `tableVisibility: GraphTableVisibility` (`"project" | "used" | "all"`) replaces the two persisted booleans; the graph toolbar shows a single labelled dropdown with the owner's three choices, in the owner's order: **Solo tabelle di progetto**, **Tabelle di progetto + tabelle di sistema usate**, **Tutte le tabelle**. A hint says framework tables are the ones the project loads from the `@facilis.dev` modules. Labels and hint are `t()` keys (en + it) like every graph string (D-043).
- **Only tables are filtered.** Routes, pages, views and workflows are never hidden by the choice — there is no route filter left to misclassify anything. `"all"` hides nothing, `"project"` hides every framework table (declared by an installed `@facilis.dev/*` package, source under `node_modules/`, the `sistema` badge), `"used"` hides only the framework tables the project does not reference.
- **The exact "used" definition.** A framework table is used when it is the target of an edge of kind `route-table`, `route-view`, `fk`, `relation` or `view-base` whose source node exists and is not a framework table. All routes are project routes, so the starter's `logout` → `sessions` edge keeps `sessions` visible in `"used"` mode; a framework→framework edge (the FK between two framework tables) never makes a table used, and an edge whose source node no longer exists does not count either.
- **Drawn view.** A hidden table removes every edge touching it; the automatic layout is computed from the visible nodes while the saved positions of the remaining nodes are kept, and `ProjectGraphStats.hiddenNodes` counts the removed nodes (0 in `"all"`). `buildProjectGraphView` treats a missing `tableVisibility` as `"all"`, and `emptyGraphLayout()` starts in `"all"`.
- **Persistence.** `.facilis/graph/layout.json` (D-126) stores `tableVisibility` in place of the two booleans; the file version stays 3. Decoding accepts a valid `tableVisibility`; otherwise a legacy `hideSystemTables === true` migrates to `"used"` and `false`/absent to `"all"`, while a legacy `hideSystemRoutes` is ignored, so no saved layout is invalidated. Encoding writes `tableVisibility` only. "Reset layout" keeps the preference exactly like `hiddenEdges`, and a hidden node keeps its saved position, so switching back restores the arrangement.

**Consequences.** No analyzer change: the classification uses facts that already exist (`framework`, `sourceFile`, `dbTables` and the graph edges), so the manifest, OpenAPI and validator are untouched. The "system route" concept disappears from the IDE graph model — the route heuristic, the two-boolean state and the route-filter branches are deleted — so no state combination can hide a route, and the owner-reported logout/sessions regression is fixed by construction and pinned by a test. Old `layout.json` files keep working: one saved with the table filter on opens in `"used"` (the closest saved intent) and one saved with the route filter on loses only that now-meaningless preference. The trade-off is that `"used"` is a projection over the drawn edges, not a semantic "unused" analysis: a framework table reached only through a framework→framework edge counts as unused, which is the intended reading of "the project does not use it". SPEC §10.2's project-graph row names the panel and its fact source, not the filter fields, so only this log and the findings doc change.

**Verification.** `pnpm --filter @facilis.dev/ide test -- graph-model-table-visibility framework-analysis` covers the three modes and the owner case: in `"used"` the analyzer graph keeps `sessions` with the `POST /api/auth/logout` → `sessions` edge, in `"project"` `sessions` is hidden while the logout route stays visible, and the route count is identical in all three modes. `pnpm --filter @facilis.dev/ide test -- graph-layout graph-layout-files graph-layout-io graph-access` covers the default `"all"`, the legacy migration (`hideSystemTables: true` → `"used"`, absent → `"all"`, `hideSystemRoutes` ignored), the round-trip that writes `tableVisibility` only, and the AI `graph_state`/`graph_arrange` shape. Prettier on the touched files. The full gates (`pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` and the file-length/theme/i18n checks) are run by the Lead before the PR.
