# Facilis todo app (Phase 1 acceptance app)

Hand-written app whose framework, server and data layers use **only** the Facilis public
packages: `@facilis/core`, `@facilis/db`, `@facilis/auth`, `@facilis/nitro` (file
attachments go through `@facilis/nitro/storage` over `@facilis/storage`); the UI is a plain
Tailwind CSS v4 + Base UI substrate. It is the Phase 1 exit criterion
(spec §12, §14.2): every route is written with `defineAuthorizedHandler`, RLS policies are
generated from the schema, auth tables and roles come from `facilis.config.ts`, and
`/_openapi.json` carries `x-db-tables` through the framework AST pass.

## Run

```bash
# from the repo root, once:
pnpm install
cd examples/todo-app
FACILIS_INITIAL_ADMIN=admin@example.com \
FACILIS_INITIAL_ADMIN_TOKEN=<one-time secret> \
PORT=5199 pnpm dev
```

One process: Vite serves the client and mounts Nitro (spec §10.6). Open
`http://localhost:5199`.

> In the sandbox the browser can only reach the `facilis.home` HTTPS vhost, which forwards to
> **port 5173**. Start this example there when you want to try it through the proxy:
> `pnpm exec vite dev --host 0.0.0.0 --port 5173` — the example's `vite.config.ts` allows
> that Host header. The vhost is shared with the IDE dev server, so only one process can own
> 5173 at a time.

> Headless note (this sandbox): Nitro inherits `PORT` (8080 is occupied) and Vite's
> `localhost` binds IPv6 `::1` — probe `http://localhost:5199`, or pass
> `--host 127.0.0.1` to `vite dev` (D-009).

## Demo flow

1. Register `admin@example.com` and send the bootstrap token in the registration body
   (`FACILIS_INITIAL_ADMIN` + `FACILIS_INITIAL_ADMIN_TOKEN` set at startup, D-150) → the first
   registration matching that email **with the token** is granted `admin`; the response is
   generic (`{ accepted: true }`) either way.
2. Register a second user → gets the `user` role from `facilis.config.ts`.
3. Each user only sees their own todos: tenant isolation is `AS RESTRICTIVE` and owner
   isolation is permissive, both driven by `app.tenant_id`/`app.user_id`/`app.roles`
   (D-008). Requests run as the non-superuser `facilis_app` role, so PGlite really
   enforces RLS (a superuser would bypass it). The tenant is the deployment's, never the
   session's, and the database fills it from `app.tenant_id` (D-040) — no route names it.

## Background jobs

`server/jobs/purge-completed-todos.ts` is a `defineJob` definition (D-107): Zod
`input`/`output`, the `tables` the sudo audit records, and a `run` body that receives the
**system-scoped** database (`facilis_system`: RLS bypassed, own transaction, audited) even
though the queue itself runs as `facilis_app`. Definitions are loaded through the
`#facilis/jobs` virtual module; an invalid or duplicate one becomes a `job_definition_invalid`
manifest warning and is skipped, never a boot failure. The design reference is
[docs/JOBS.md](../../docs/JOBS.md).

The framework exposes `ctx.jobs` to server code only, so this app puts its own authenticated
surface over it:

| Route | Does |
|---|---|
| `POST /api/jobs` | Enqueue `purge-completed-todos` (`olderThanDays`, optional `runAt` ISO instant) -> `{ id }` |
| `GET /api/jobs/:id` | The serialized `JobRecord` (status, input, attempts, timestamps) |
| `DELETE /api/jobs/:id` | Cancel a queued job or abort a running one -> `{ cancelled: true }` |

The `jobs` section of `facilis.config.ts` shows every key once: `maxConcurrent`,
`maxAttempts`, `retryDelayMs`, `timeoutMs`, `pollIntervalMs`, `persist`. With
`persist: true` the queue lives in `facilis_jobs`, which `db/schema.ts` re-exports from
`@facilis/db`, so `pnpm db:generate` owns its DDL (`0002`: the queue table + its RLS policy).
Queue state survives the dev-server worker reload; a missing table degrades to the in-memory
store with a `jobs_table_missing` manifest warning.

## File attachments (D-053, SPEC §5.10)

Binary uploads are content-addressed and never stored in Postgres: `facilis_files` holds
the metadata and the bytes live in storage addressed by their sha-256 hash. A todo
"contains" files through `todo_files`, the link table generated by
`fileLinks(todos, { table: "todo_files", column: "todo_id" })` — cascading FKs to `todos`
and `facilis_files`, a restrictive tenant policy and a `parent_access` policy that
evaluates the todo's own RLS (so a link is visible exactly when its todo is).

The `storage` section of `facilis.config.ts` sets these keys:

| Key | Value here | Meaning |
|---|---|---|
| `driver` | `"local"` | `"local"` writes `<project>/.facilis/binary/<hh>/<hash>` (the VFS/OPFS mirror persists it, D-052); `"s3"` writes `blobs/<hash>` in an S3-compatible bucket |
| `maxUploadBytes` | 5 MiB | per-upload limit; a larger upload is `413 file_too_large` |
| `tokenTtlSeconds` | 300 | lifetime of a signed download URL (default 5 minutes) |
| `encryption` | off (default) | opt-in at-rest encryption (D-117); the example leaves it disabled, so blobs are stored as plaintext |

Production sets `storage.driver: "s3"` with `bucket`, `region` and (optionally)
`endpoint`/`forcePathStyle` for R2 or MinIO, plus the environment secrets
`FACILIS_STORAGE_SECRET` (HMAC key for the download tokens),
`FACILIS_S3_ACCESS_KEY_ID` and `FACILIS_S3_SECRET_ACCESS_KEY` (optionally
`FACILIS_S3_SESSION_TOKEN`). Credentials never go in the committed config.

At-rest encryption is opt-in and **off here**. To try it locally, set
`storage.encryption: { enabled: true }` in `facilis.config.ts` and export
`FACILIS_STORAGE_ENCRYPTION_KEY` (a 32-byte key as base64 or 64-character hex) before
`pnpm dev`; `FACILIS_STORAGE_ENCRYPTION_KEY_ID` (default `primary`) labels the active key
and `FACILIS_STORAGE_ENCRYPTION_RETIRED_KEYS` (JSON `{ "keyId": "key" }`) keeps older blobs
decryptable after a rotation. The key must be stable across restarts — encryption needs an
explicit key even in dev. Consequences: the stored sha-256 hash covers the ciphertext, so
identical uploads are no longer deduplicated (`facilis_files.size` stays the plaintext size);
the download route always proxies and decrypts instead of redirecting to a presigned S3 GET;
and blobs uploaded before encryption was enabled are refused (the decrypt stream throws and
the download fails — there is no plaintext fallback) and must be re-uploaded. Enabling it
without a usable key warns `storage_encryption_key_missing`/`storage_encryption_key_invalid`
and degrades only the file routes. SPEC §5.10 and D-117 are the contract.

Uploads and downloads stream end to end (D-117): the platform parses the multipart form once
(bounded by `maxUploadBytes`) and the file is then hashed/encrypted while it is written;
`sendStoredFile` streams the plaintext response with `content-length` from
`facilis_files.size`. An S3 PUT stages the upload stream (ciphertext when encryption is on)
to a `0600` temp file while hashing and counting it — SigV4 needs the payload hash and length —
uploads from that file and deletes it. Nothing in the framework's storage/crypto path buffers
the whole file.

| Route | Does |
|---|---|
| `POST /api/todos/:id/files` | `multipart/form-data` with one `file`: verifies the todo is visible, stores the blob and inserts the link -> `StoredFile` (`id`, `name`, `mime`, `size`, `url`) |
| `DELETE /api/todos/:id/files/:fileId` | detaches the file; drops the metadata row when no other link references it -> `{ deleted: true }` |
| `GET /api/files/:id?token=...` | token-only download proxy: streams the blob in dev, redirects to a presigned S3 GET in production; with encryption enabled it always streams and decrypts (no presigned redirect) |

`GET /api/todos` carries each todo's `files` with a freshly signed `url` (`null` when no
storage driver booted). The URL is signed and short-lived, which is why a plain
`<a download>` works: GET is token-only by design, while every mutation stays
session-authenticated. Upload failures reuse the `errors.*` catalogue
(`errors.file_too_large`, `errors.storage_unavailable`).

## Layout

```
db/schema.ts             todos + re-exported auth tables/facilis_jobs/facilis_files, RLS, enableRLS
db/migrations/           0000: DDL + policies; 0001: tenant defaults + role seed; 0002: facilis_jobs;
                         0003: facilis_files + todo_files (policies included)
server/jobs/             defineJob definitions loaded through #facilis/jobs (D-107)
server/routes/api/...    defineAuthorizedHandler only (todos, attachments, auth, jobs)
src/main.tsx             bootstrap: theme + i18n + router
src/app.tsx              one explicit route table + session provider + Toaster
src/pages/               one file per route (login, register, todos, not-found)
src/layouts/             project-owned shell (header/nav/session)
src/components/          app-specific controls (theme toggle, locale switch, todo attachments)
src/components/ui/       shadcn-style primitives copied into the project (Base UI)
src/lib/                 api fetch wrapper, session guards, theme, i18n, dates
src/lib/*.test.ts        unit tests for the pure helpers
src/styles.css           Tailwind v4 entry + role tokens (the only stylesheet)
locales/en.json, it.json flat i18n keys, exact parity
facilis.config.ts        roles/permissions/db/i18n (SPEC Appendix B)
scripts/verify-headless.sh   boots the app and asserts the whole Phase 1 contract
```

## Frontend organisation

The client is organized as `pages` (route components, data + view), `layouts` (shells
that know the router and the session), `components` (app-specific pieces) and `lib` (pure
logic: one fetch wrapper, session guards, theme, i18n, dates).

The UI layer is **Tailwind CSS v4 + Base UI**. The shadcn-style primitives live in
`src/components/ui/` and are copied into the project: the app owns them and edits them
directly, so there is no component package to install and no `components.json`. Theme role
tokens (`--background`, `--primary`, the radii, the font) live in `src/styles.css` and
components only name roles, so the `[data-theme="dark"]` block restyles everything.
There is no UI kit package: the components live in the project. Dates go
through `@facilis/time`, never `Date#toLocaleString`, and every user-facing string is a
`t()` key present in both catalogues. The full contract is
[`docs/FRONTEND.md`](../../docs/FRONTEND.md) (D-058).

The UI shows: register → auto-login → todos (create with optional due date, toggle, delete,
overdue badge, toasts), light/dark theme toggle, en/it language switch, empty/loading/error
states, and `/login` redirecting an authenticated session to `/todos`.

## Verify it headlessly

```bash
./scripts/verify-headless.sh     # FACILIS_VERIFY_PORT=5199 by default
```

It checks: health + revision, full manifest with no warnings, `?format=summary` budget
(<2000 chars), ETag/304, invalid `sections` 400, cross-origin 403, `/_openapi.json`
`x-db-tables`/`x-permission`, registration with `FACILIS_INITIAL_ADMIN` + token -> admin, default
role for a second user, login/session permissions, todo CRUD, RLS isolation (the second user
sees nothing, cross-user DELETE is 404), binary attachments (multipart upload, byte-for-byte
download through the signed token URL, attachment in the list, cross-user upload 404,
token-less 400 and tampered-token 404, delete), a future-scheduled job that is enqueued,
inspected, cancelled and observed as `cancelled` without racing the scheduler,
input-validation 400s and anonymous 401.
