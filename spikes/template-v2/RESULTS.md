# Template v2 — WebContainer verification

Does the **v2 generated project** (Tailwind CSS v4 + Base UI + shadcn-style copy-in components)
actually install, boot and hot-reload in the real Studio? This run answers it without mocks:
`spikes/template-v2/run.mjs` drives the Studio through CDP, creates a project from the IDE's
Home screen, waits for the in-VM npm install and Vite dev server, inspects the preview, then
writes a NEW utility class into `src/app.tsx` through the VFS and checks the computed style.

**Result: 29/29 checks pass, including the HMR workaround.**

## Run

```
node spikes/template-v2/run.mjs
```

Environment: Facilis Studio dev server from this checkout, Chrome under
`/tmp/facilis-dev/browser`, fresh project profile. The project was generated by the IDE from
`examples/todo-app` (D-062), i.e. exactly what a user gets.

## What the run proves

- the v2 dependency set installs in the VM: `@base-ui/react` 1.9.0, `tailwind-merge`,
  `class-variance-authority`, `clsx`, `sonner`, `lucide-react`, Geist, and the Tailwind trio;
  `@tailwindcss/oxide-wasm32-wasi` 4.3.3 resolves because the VM reports `process.arch = wasm32`;
- the generated `package.json` is v2: no `@facilis/ui`, and `tailwindcss`, `@tailwindcss/vite`,
  `@tailwindcss/oxide-wasm32-wasi` are all pinned to the **same exact** version;
- `src/styles.css` is the Tailwind entry and the preview paints the direction-A theme
  (`rgb(247, 248, 249)` canvas) with Geist loaded and **no legacy `.fc-*` class**;
- the smoke contract survives: the injected
  `<p className="muted">Edit src/app.tsx and save to test HMR.</p>` is rendered;
- the generated project ships `vite-plugins/tailwind-rescan.ts`, and it works: writing
  `bg-[#123456]` into `src/app.tsx` through the VFS changed the computed background to
  `rgb(18, 52, 86)` **without touching `src/styles.css`**.

## The HMR workaround

The first version of the plugin invalidated the CSS module and called `server.reloadModule`.
That is **not** enough: the preview kept the old stylesheet (`bg-[#123456]` missing, background
transparent) although the DOM class changed, and touching `src/styles.css` fixed it — the
signature of [tailwindlabs/tailwindcss#20605]. The Vite plugin only recreates its compiler and
scanner when a build dependency's mtime moves, and the WASI scanner instance otherwise keeps the
old candidate set.

The shipped workaround therefore rewrites `src/styles.css` with its own bytes (content unchanged,
mtime moved) after a debounced `.ts/.tsx` change, only when `process.arch === "wasm32"`. Vite sees
a normal stylesheet change, `@tailwindcss/vite` rebuilds with a fresh scanner, and the new
utility reaches the preview as a CSS HMR update. On the host the plugin is a no-op and
`vite build` never runs it (`apply: "serve"`). A fork of Tailwind was rejected: this is one
dev-only scanner bug, the workaround is a few dozen lines, and it can be deleted when upstream
fixes it.
